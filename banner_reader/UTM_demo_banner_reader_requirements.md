## 1. 背景と目的

### 1.1 背景

学会・展示会でポスターやバナーを撮影する行為は、研究者・学生を問わず日常的に行われている。しかし撮影された画像は構造を持たないため、後から検索・比較・集計ができず、事実上二度と開かれない。**撮影量が多い者ほど、記録されない情報の損失が大きい。**

### 1.2 目的

撮影画像から読み取れる情報を構造化データに変換し、検索可能な台帳として蓄積する手段を提供する。あわせて、本システムの構築過程を通じて「AI が下書きを作り、人が決定し、検証する」という制作の形を、UTM CEE の聴衆に対して実演する。

### 1.3 本システムが行わないこと

読み取った情報に対する**解釈・推薦・評価を行わない**。「この研究者と接触すべき」「この製品は有望である」といった判断は提供しない。読み取れた事実と、読み取れなかった空欄を、そのまま提示する。解釈は利用者が行う。

## 2. スコープ

### 2.1 対象

- スマートフォンからの画像撮影・送信
- 4 種別（国際会議バナー／研究発表ポスター／企業展示パネル／名刺）の判別と項目抽出
- 抽出結果の確認・修正・保存・一覧・検索・削除・書き出し
- 講演当日のライブ機能追加とデプロイ

### 2.2 対象外

| 項目 | 理由 |
|---|---|
| 会場参加（聴衆の端末からの投稿） | 2026-09-20 決定。運用負荷と個人情報リスクを回避 |
| 推薦・マッチング機能 | 1.3 のスタンスによる |
| 翻訳機能 | 原文の言語のまま記録する方針 |
| ユーザ認証・アカウント管理 | デモに不要 |
| 画像の永続保存 | プライバシー方針による（送信 → 読み取り → 破棄） |
| PC 専用画面 | モバイル前提。PC でも開けるが最適化しない |
| 教員向けステップ 2・3（ルーブリック／採点） | 同一リポジトリ・同一 Worker に同居するが、パスとコードは分離する |
| 独立したリポジトリ・Worker の新設 | 既存の自動デプロイ経路を流用する（2026-09-20 決定） |

| 利用者 | シーン | 使う機能 |

| 研究者・教員 | 学会会場でポスターを撮る。展示会で企業パネルと担当者の名刺を撮る | 撮る・確かめる・束ねる・書き出す |

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| エントリ | 1 回の撮影・送信で生成される 1 件の記録。画像 1〜4 枚に対応 |
| 種別（type） | エントリの分類。`conference` / `research` / `exhibition` / `card` / `unknown` |
| フィールド | 抽出項目。`{ value, sourceText, confidence }` の三つ組で保持する |
| sourceText | 画像上に実際に書かれていた文字列。人が照合するための根拠 |
| confidence | 読み取りの確信度（0.0〜1.0） |
| 検証済み（reviewed） | 人が内容を確認・修正した状態。`reviewedBy: "human"` |

## 5. 機能要件

優先度：**MUST**（当日までに必須）／**SHOULD**（あることが望ましい）／**COULD**（時間があれば）

### 5.1 撮影・送信

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | 撮影ボタンのタップで端末のカメラを直接起動できること | MUST |
| FR-02 | 撮影済み画像の選択も可能であること（サンプル画像の投入に使用） | MUST |
| FR-03 | 1 エントリにつき画像を 1〜4 枚まで受け付けること | MUST |
| FR-04 | 送信前にサムネイルで確認でき、個別に取り消せること | SHOULD |
| FR-05 | 送信前に端末側で画像を縮小すること（長辺 1,600 px、JPEG 品質 0.8） | MUST |
| FR-06 | 送信中に処理段階を文言で表示すること（`Uploading…` → `Reading…` → `Organising…`） | MUST |

### 5.2 読み取り

| ID | 要件 | 優先度 |
|---|---|---|
| FR-07 | 画像から種別を自動判定し、`type` と `typeConfidence` を出力すること | MUST |
| FR-08 | 判定した種別に対応する項目のみを抽出すること（§7.2 の項目定義に従う） | MUST |
| FR-09 | 名刺が含まれる場合、種別に関わらず `contacts[]` に人物情報を格納すること | MUST |
| FR-10 | 全フィールドに `sourceText` と `confidence` を付与すること | MUST |
| FR-11 | 読み取れない項目は `null` とし、**推測による補完を行わないこと** | MUST |
| FR-12 | 数値は単位を含めて記録し、丸めないこと | MUST |
| FR-13 | 原文の言語のまま記録し、翻訳しないこと | MUST |
| FR-14 | 不鮮明・見切れで読めなかった領域を `unreadable` に記録すること | SHOULD |
| FR-15 | 複数枚を 1 回の API 呼び出しで処理し、1 つの JSON を返すこと | MUST |

### 5.3 確認・修正

| ID | 要件 | 優先度 |
|---|---|---|
| FR-16 | 抽出結果を項目ごとにカード形式で表示すること | MUST |
| FR-17 | 確信度を視覚的に区別すること（高＝通常／中＝注意表示／低・空欄＝未確定表示） | MUST |
| FR-18 | 各項目に `sourceText` を併記し、人が照合できること | MUST |
| FR-19 | 項目をタップしてその場で値を修正できること | MUST |
| FR-20 | 修正時は `value` を上書きし `confidence` を 1.0 に、`sourceText` は保持すること | MUST |
| FR-21 | 1 項目でも修正されたエントリに `reviewedBy: "human"` を立てること | SHOULD |

### 5.4 蓄積・活用

| ID | 要件 | 優先度 |
|---|---|---|
| FR-22 | エントリを保存できること | MUST |
| FR-23 | 保存済みエントリを新着順に一覧表示し、件数を表示すること | MUST |
| FR-24 | 種別タブで絞り込めること（All / Conference / Research / Exhibition / Card） | MUST |
| FR-25 | キーワードで検索できること（`title` / `org` / `tags` / `summary` を対象） | SHOULD |
| FR-26 | エントリを削除できること（一覧・詳細の双方から） | MUST |
| FR-27 | CSV / JSON で書き出せること（種別ごとに列構成を切り替える） | SHOULD |
| FR-28 | 送信結果を受信と同時に `localStorage` に下書き保存すること | COULD |

## 6. 非機能要件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 性能 | 画像 1 枚で 15 秒以内、4 枚で 35 秒以内に結果を返すこと。超過時も進捗表示で待機状態が分かること |
| NFR-02 | 対応環境 | iOS Safari（最新 2 バージョン）、Android Chrome（同）で動作すること。**当日使用する講演者の端末で事前確認を必須とする** |
| NFR-03 | モバイル操作性 | 1 画面 1 カラム、横スクロールなし。タップ領域 44 px 以上、入力欄フォント 16 px 以上（iOS の自動ズーム防止） |
| NFR-04 | 可用性 | 会場ネットワーク不調時に備え、事前投入済みエントリと完成画面の録画を用意すること |
| NFR-05 | セキュリティ | OpenAI API キーは Cloudflare Secret に格納し、クライアントに露出させないこと |
| NFR-06 | プライバシー | **画像をサーバに保存しないこと**（送信 → 読み取り → 破棄）。エントリは KV の `expirationTtl` により 24 時間で自動失効させること（講演者の事前投入分を除く） |
| NFR-07 | 費用 | `gpt-4.1-mini` を既定とし、1 回あたり数セント程度に収めること。OpenAI 側に使用上限アラートを設定すること |
| NFR-08 | 保守性 | `openai.js` / `store.js` / `app.css` は**本システムで新規作成する**（リポジトリに未存在のため）。教員向けステップ 2・3 からも使えるよう汎用に書き、Banner Reader 固有のコードは `src/banner/` と `public/banner/` に閉じ込めること |
| NFR-09 | 堅牢性 | Structured Outputs（strict）を用い、JSON 構造の破綻を防ぐこと。Worker 側で最終検証を行うこと |
| NFR-10 | 開発速度 | 当日のライブ追加が「依頼 → push → 自動デプロイ」で 5 分以内に完了すること |
| NFR-11 | 前提整備 | 保存系（FR-22〜FR-27）は KV 名前空間 `DEMO_KV` を前提とする。**2026-09-20 に作成・バインディング済み**（id `bb70c238…`、`remote: true`）。KV が使えない事態では無状態の読み取りのみで縮退運転する |

## 7. データ要件

### 7.1 保持するデータ

| 種類 | 保存先 | 保持期間 |
|---|---|---|
| エントリ（構造化 JSON） | Cloudflare KV `entry:<id>` | 24 時間（事前投入分は無期限） |
| 索引 | KV `idx:all` / `idx:type:<type>` | 同上 |
| 画像 | **保存しない** | — |
| 送信結果の下書き | 端末の `localStorage` | 端末側の管理に委ねる |

### 7.2 項目定義

基本設計書 §3.2〜3.6 の定義に従う。要約すると次の通り。

- **共通**：`type` / `typeConfidence` / `language` / `title` / `org` / `summary` / `tags` / `urls` / `capturedAt` / `unreadable`
- **conference**：会議名・略称・回次・会期・開催地・会場・主催者・目的・トピック・キーノート・締切・参加費・URL
- **research**：タイトル・著者・所属・研究の問い・手法・対象・主要結果・結論・限界・キーワード・資金・連絡先
- **exhibition**：企業名・所在・製品名・用途・目的・効能・達成できること・新規性・応用可能性・技術要素・導入実績・認証・URL
- **contacts[]**：氏名（原語／ラテン）・役職・部署・組織・住所・電話・メール・Web・SNS

### 7.3 フィールドの共通形

すべての値は `{ value, sourceText, confidence }` の三つ組で保持する。

- `value` — 読み取った値。読めなければ `null`
- `sourceText` — 画像上にあった文字列そのまま。人が照合するための根拠
- `confidence` — 0.0〜1.0

人が修正した場合は `value` を上書きし、`confidence` を `1.0`、エントリの `reviewedBy` を `"human"` とする。`sourceText` は保持する（何が書いてあって、人が何に直したかが両方残る）。

## 9. 制約・前提

1. 講演当日（2026-09-21）までに完成させる。実装可能な範囲を優先度で切る
2. 操作はスマートフォンから行う。PC 専用画面は作らない
3. 会場参加を行わないため、当日に投入される画像は**講演者が用意したサンプルと、講演者自身のスマートフォンで撮影した画像に限られる**
4. サンプル画像は**公開を前提とした素材に限る**（学会の CFP バナー、展示会の公式告知など）。名刺は架空のものを用意する
5. 学会ポスターには撮影禁止の場合がある。この判断は人が行う旨を講演で述べる
6. 教員向けステップ 2・3 と同じリポジトリ・同じ Worker 上に同居させる
7. **既存の動作を壊さない。** Banner Reader は `src/banner/` と `public/banner/` に閉じ込める。既存ファイルへの変更は `src/index.js`（ルーティング追加。`/api/health` は維持）、`public/index.html`（入口カード追加・`:root` の切り出し）、`wrangler.jsonc`（KV バインディング追加）の 3 点に限る
8. **2026-09-20 時点でリポジトリは骨組みのみ**である（`src/index.js` は `/api/health` のみ、`public/index.html` のみ、KV 未設定）。教員向けステップ 1〜3 は未実装であり、本システムが最初の本格的な機能となる

## 11. 当日運用要件

### 11.1 実装の切り分け（A 案を採用）

| 区分 | 内容 |
|---|---|
| **事前に `main` へ投入** | `/api/banner/capture`、保存・一覧・検索・削除・書き出し、全画面。すなわち FR-01〜FR-28 の実装済み分すべて |
| **当日ライブで追加** | 決め打ちの機能 1 つ（§11.2） |

当日は「ゼロから作る」ではなく「**動いているものに機能を足す**」を見せる。所要時間が読め、失敗リスクが最小になる。

### 11.2 ライブで追加する機能（決め打ち）

**研究発表ポスターに「使用装置・ソフトウェア」欄を追加する。**

| 項目 | 内容 |
|---|---|
| 変更箇所 | `src/banner/schema.js`（`research` に `instruments` を追加）、`public/banner/entry.html`（表示 1 箇所） |
| 所要 | 依頼 → push → 自動デプロイで 5 分以内 |
| 見せ方 | **追加前に読み込んだ同じ画像を、追加後にもう一度読み込む。** 同じ画像から新しい項目が現れる |
| 選定理由 | 工学系の聴衆にとって実用的であり、かつ「ポスターに書いてあることを読むだけ」という本システムのスタンスを外さない |

**予備**（時間が余った場合／上記が早く終わった場合）：一覧の CSV 書き出しにおける種別ごとの列切り替え。

### 11.3 フォールバック

| 事象 | 対応 |
|---|---|
| KV が間に合わない | 無状態の `/api/banner/capture` のみで実施。一覧は `localStorage` に退避し、24–28 分の「蓄積」パートを短縮する |
| 会場ネットワーク不調 | 事前投入済みエントリの表示と、完成画面の録画を再生 |
| デプロイが通らない | `demo-complete` ブランチに追加機能込みの完成版を用意し、切り替えてデプロイ |
| API 応答が極端に遅い | 録画に切り替え、待ち時間を解説に充てる |

### 11.4 進行（30 分）

| 時間 | 内容 |
|---|---|
| 0–3 分 | 問題提起。撮りっぱなしの写真。オートフォーカスを最も必要としたのはプロの写真家だった |
| 3–8 分 | 完成版の実演。講演者のスマートフォンで会議バナー・研究ポスター・企業展示＋名刺を順に読み込む |
| 8–18 分 | ライブで「使用装置・ソフトウェア」欄を追加し、同じ画像を読み直す |
| 18–24 分 | 人が確かめる。確信度の低い項目を `sourceText` と照合して修正。空欄が空欄のまま出ることの意味を述べる |
| 24–28 分 | 蓄積の意味。一覧・種別タブ・書き出し。設計判断としての個人情報の扱いに触れる |
| 28–30 分 | 締め。「AI builds. People decide, and examine.」 |
