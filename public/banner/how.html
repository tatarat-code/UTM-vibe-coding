The shape of the work

One loop, repeated per stage

Vibe coding does not remove engineering work. It moves it to the two ends of the loop, where a person still has to say what is wanted and whether what came back is true.

Human

Decide

What it is, what it will never do, what counts as correct.

AI

Build

Generate the code for one stage, in writing, against the spec.

Human

Examine

Run real data, including the case where the answer should be empty.

The loop closes at every stage, not once at the end. A stage that cannot be examined is not finished.

Step 1

What it will never do

An AI will gladly add features nobody asked for. Ruling them out on day one is what keeps a demo from quietly becoming a different product.

Banner Reader does

  • Read what is printed on a photograph
  • Keep the evidence beside every value
  • Let a person correct any field
  • Keep records searchable by type and keyword

Banner Reader will not

  • Interpret, recommend or rank anything
  • Translate — the original language stays
  • Fill a blank from general knowledge
  • Keep the image after reading it
Step 2

Requirements you can test

If you cannot state what would count as a wrong answer, you cannot judge what the AI hands back. Three of the rules Banner Reader was built against:

FR-11

Unreadable fields stay null. Inference is forbidden. — MUST

NFR-06

Images are never stored on the server: sent, read, dropped.

AC-03

Given a deliberately blurred field, the output stays empty and says so.

Step 3

Design the data before the screens

Every extracted value carries the text it came from and how certain the reading was. A value without its evidence cannot be checked by a person — so a field without sourceText is not allowed to have a value at all. 

{
  "value":      "±0.5 °C",
  "sourceText": "Accuracy ±0.5 °C",
  "confidence": 0.95
}

// no sourceText → no value.
// Enforced on the server,
// not only asked for.

Why this shape

  • A person can check any value against the photograph
  • Low confidence can be shown, not hidden
  • A correction keeps the original text beside it: what was printed and what a person made of it both survive
  • The record stays honest when the reading fails
Step 4

Prepare the ground before the first prompt

Generated code is worth little until it can be run, deployed and checked in about a minute. Set that up first.

commit→push→automatic build→live URL, 1–2 min

Ready before prompting

  • Repository with deploy on push
  • API keys held by the platform, never in the repo or the prompt
  • Storage bound and reachable

Samples with known answers

  • Four fictitious images, one per type
  • One poster with its funding box deliberately blurred
  • One card with a decorative QR code that cannot be decoded
  • A wrong answer is therefore visible, not merely possible
Step 5

Hand over in writing

The handover document had six parts. Each one prevents a specific kind of drift.

1

What to read first

And which document wins when two disagree.

2

Confirmed facts

URLs, bindings, what already exists and must not be rebuilt.

3

Order, and where to stop

"Stage 4 is enough for tomorrow. Aim there first."

4

Absolute rules

No inference, no stored images, these files only.

5

How to verify

Which samples, which criteria, what a correct failure looks like.

6

Process

Commit per stage. Ask before changing the specification.

Step 6

Stages that can stop anywhere

The order was chosen so that running out of time costs features, not the demo.

1–3 · Model wrapper, field definitions, capture API

An image goes in, a structured record comes out.

4 · Capture and review screens

Photograph, read, check, correct — on a phone, with no storage yet.The demo works from here

5–6 · Storage, list, search, delete

Records accumulate and can be found again.

7–8 · Export, and the way in from the front page

CSV and JSON, with columns that follow the type.

What examination caught

Four defects in code that read correctly

None of these were visible by reading the source. All four came from running real data.

Looked fineBilingual panel read cleanly, every field populated.
Actually didSilently translated Japanese into English, and dropped two Japanese bullet points. Broke the "keep the original language" rule.
Looked fineSaving a record returned success.
Actually didWiped every field on the way in: the save path read the wrong shape of the record.
Looked fineFive records saved, five confirmations.
Actually didTwo vanished from the list. A shared index document lost updates under eventual consistency.
Looked fineA button was hidden in code.
Actually didStayed on screen: a CSS rule outranked the hidden attribute.
The general lesson

Rules in code, not only in the prompt

A rule you can only ask for is a rule you do not have.

Asked for — the prompt

"If a value is not legible, set it to null. Never fill a blank from general knowledge."

↓
Enforced — the server

Any value that arrives without its sourceText is dropped before the record is returned. A correction made by a person is the one exception, and it is marked as one.

Step 8

Design for the change that happens in front of an audience

One file defines every field. From it come the schema sent to the model, the prompt, the server-side validation and the screen. Adding a whole new extracted field is one line. 

// src/banner/schema.js — the only place fields are defined
f("instruments", "Instruments and software", "…", MULTI),

Before

  • The poster's equipment list sat inside a block of method text, unsearchable.

After — same photograph, read again

  • Ten named instruments and software packages, each with the text it was read from.
Judgement

What the machine must not do

A tool that reads whatever is put in front of it creates a duty to decide what it should read. These are decisions, not limitations.

  • An unreadable field stays empty
  • No image is kept on the server
  • Records expire 24 hours after they are saved
  • Delete is always one tap away
  • Evidence is stored beside every value
  • QR codes and logos are never decoded
Failure modes

How this procedure goes wrong

  • Judging output by whether it looks plausible
  • Letting the AI write both the code and the acceptance criteria
  • A plan with no working stopping point
  • Secrets in the repository or in the prompt
  • Treating a prompt instruction as a guarantee
  • One large commit, with nothing to roll back to
  • Letting the specification change silently during generation

Read a poster yourself

Photograph a banner, a poster, an exhibition panel or a business card. Watch which fields come back empty — and notice that this is the feature.
